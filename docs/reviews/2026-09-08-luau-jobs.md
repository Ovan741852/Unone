# Luau jobs implementation evidence — 2026-09-08

## Delivered

Optional `api.jobs` with real game-owned Luau buffer computation; native two-thread
pool; Web inline execution; next-tick deterministic delivery; explicit limits,
cancellation, reset, hot-reload isolation and AI-readable diagnostics. See the
[contract](../jobs.md) and [Jobs Lab](../../_Games/jobs-lab/README.md).

## Performance experiment

Release Rust, seed 42, same Jobs Lab payload, four 1024-value integer batches each
tick. Verification off, 20 warmup + 120 measured ticks, three alternating pairs.
This measures native runtime tick throughput without a renderer. Each pair compares
an internally forced inline isolated executor against the native pool. All 360
measured per-tick observation digests match between those two modes.

| Pair | Inline mean / p95 ms | Threads mean / p95 ms | Mean reduction |
| --- | --- | --- | --- |
| 1 | 4.679 / 6.091 | 2.756 / 3.584 | 41.1% |
| 2 | 4.658 / 5.978 | 2.556 / 3.366 | 45.1% |
| 3 | 5.305 / 6.880 | 3.510 / 4.425 | 33.8% |

A single direct main-Luau reference run before those pairs averaged **3.383 ms**.
Its gameplay checksum matches each tick, but its job state intentionally differs.
That reference is not an alternating, repeated performance comparison: these
numbers do **not** establish a reliable gain over direct main-Luau computation.
They expose the tradeoff: fresh VM creation, compilation, safe-point accounting
and copying can consume much of the parallelism benefit. Small jobs should stay
in ordinary game Lua. Browser and mobile FPS are not measured by this benchmark.

[Raw timings, limits and payload hash](2026-09-08-luau-jobs-benchmark.json).
Reproduce with `cargo test --release -p unone-engine native_pool_benchmark --lib -- --ignored --nocapture`.
The benchmark's inline switch is private test code, not a public native backend setting.

## Correctness and actual products

- Engine library: 215 passed, 3 ignored (including the manual release benchmark).
- Seven job tests cover input copying, native/inline per-tick equality, phase and
  capacity errors, cancellation/reset, memory/budget failures, VM isolation,
  transactional reload and profile-window freezing.
- Core-only feature configuration: six feature tests passed; jobs are optional.
- Developer JavaScript API: five tests passed.
- Jobs Lab: four test checkpoints, frames 1, 2, 30 and 120.
- Development and production selected-feature WASM builds passed actual exported
  host-payload/CLI observation parity at all four checkpoints. Production verifier
  also checks that development ABI exports are absent.
- Real browser development export: reached frame 787 with **3144** byte-verified
  batches and no runtime error; reports `wasm-inline`, `parallel:false`.
- Invoked the real browser's registered Luau verification checkbox via WebMCP.
  A four-step profiling window reported 16 completed jobs / 65536 output bytes;
  after stopping and stepping twice more, totals stayed frozen.

## Limits of this evidence

No Web Worker backend, arbitrary WASM module loader, ECS integration, hard
wall-time cancellation, Android device benchmark or general game FPS gain is
claimed. The native next-tick barrier can block the host. Payload reservation is
not total RSS. Job timings do not enter replay equality. Existing games with jobs
disabled omit the new snapshot field. The demo is an execution/validation lab,
not a claim that parallel jobs improve the ten-thousand-unit battle.
