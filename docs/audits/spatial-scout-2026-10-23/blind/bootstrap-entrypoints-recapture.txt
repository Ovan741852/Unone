# Agent instructions

## Branching policy

This project does not use feature branches. Develop directly on the
default branch (`main`). Do not create, switch to, or push new
branches unless the user explicitly asks for one.

This applies to all coding agents working in this repo, including
Claude Code and Codex.

## Default game presentation

Use the official Unone player for game presentation. Start with
`game platform snapshot`, inspect the project's presentation settings, and
follow [the AI workflow](docs/ai-workflow.md) and [player export](docs/player-export.md).
A passing headless replay does not prove that a player rendered the game.
Validate the exported official player on the requested target before reporting
visual completion.

For exhaust, sparks, explosions, trails, smoke and auras, first search
`game api search "explosion"` / `game api search "particle"`, describe the matching
APIs, and use scene `particle_effects` with `api.particle.*`. Inspect
[Particle Lab and the declarative format](docs/native-particles.md) before
implementing an effect from scratch. Keep the particle system enabled when the
game uses it. Effekseer is an optional external-asset path with host-specific
requirements, not the default answer to every effect request.

Game code declares presentation and uses engine APIs. GPU contexts, draw calls,
shader compilation, material resources and renderer lifetime belong to the
engine's presentation layer. Custom shaders must use the engine's supported
shader interface; a shader request does not authorize writing a replacement
renderer. If a required shader feature is unsupported, report the specific gap
and extend the reusable engine interface rather than silently adding game-owned
WebGL/OpenGL/WebGPU plumbing.

Replace the official renderer only as an explicitly selected extension mode for
a stated project requirement. Declare `renderer_mode: "custom"`, `renderer_module` and the complete
`renderer_files` inventory in `player.presentation.json`; see the
[selection contract](docs/ai-workflow.md#renderer-selection-and-replacement).
Do not infer renderer replacement from "make it look better", "use shaders", a browser
target, or an example of a low-level graphics API. Preserve and report the
chosen renderer and its visual verification scope in the handoff.

## Engine versus gameplay ownership

Before adding any engine capability, first classify it as gameplay/business
logic or a reusable engine primitive, and explain that classification. Do not
move a single game's behavior into Rust merely because it is convenient.

Gameplay rules belong in Luau: projectile speed, acceleration/gravity choices,
integration policy, firing, lifetime, damage, hit responses, effect selection,
cooldowns and scoring. Rust may provide reusable geometry/collision queries;
the presentation layer may provide reusable rendering such as Bloom and asset
decoders. Neither should encode this game's rules or resource choices.

When ownership is unclear, keep the behavior in Luau until a concrete reusable
requirement justifies an engine primitive. This is a design check, not a request
to ask the user for permission before every routine change.

## AI-first layout decisions

Start shared controls with the official `@unone/ui` pure Luau package, bundled
with Core and the SDK. Search `game api search "UI package"` / `"shared components"`
/ `"button component"` / `"card component"` / `"官方UI套件"` / `"共用元件"` /
`"主題樣式"`, describe `ui.components.info` and `ui.components.create`, and read
[the package contract](docs/ui-components.md). Declare the exact package version
in `project.unone.json` (`"runtime_packages":{"@unone/ui":"0.4.0"}`). Both
`api.ui.components` and the themed kit returned by `create` expose typed
text/button/slider/combobox/panel/image/component/screen constructors, the
`createSlider` numeric control, `createResponsiveLayout` model, plus
scrollView/virtualList/virtualGrid wrappers. Search `"create button"` /
`"slider drag"` / `"slider value"` / `"滑桿拖曳"` / `"下拉選單"` /
`"virtual list"` for the actual methods.
This is not an npm
module or a new renderer. Keep themes, content, application state, action meanings and
authored semantic grouping in project Luau. Custom factories remain valid.

For responsive composition search `"responsive layout"` / `"breakpoints"` /
`"row column grid layout"` / `"自適應排版"`, describe
`ui.components.createResponsiveLayout`, and read
[the shared responsive contract](docs/ui-responsive.md). Create one
`UiResponsiveLayout<T>` from typed authored variants and retain it; call
`resolve(api.ui.getViewport(),bounds?)` in the pure View. Pass `result.rect(id)`
to leaves and `result.viewport(id)` to scroll helpers. The package owns aspect
selection and explicit row/column/grid arithmetic; do not copy breakpoint tests,
coordinate conversion or region sizing into every project. Projects own semantic
groups, thresholds and complete typed `values` records, including typography
choices. A component never lays out its children implicitly. Use explicit
`space="scroll"` for local content; layout lengths are per-axis rectangle units,
not `UiStyle` vertical units. No intrinsic text measurement or automatic wrapping
is provided. Strictly increasing thresholds start at `minAspect=0`; an exact
boundary selects the new variant. Unknown fields and overflow fail explicitly.

For button activation search `"button click"` / `"button pressed"` / `"按鈕點擊"`
/ `"按下瞬間"` and use `api.input.wasPressed(action)` in `Game.update`.
`wasReleased(action)` reads release edges and `isDown(action)` reads held state.
These are non-consuming current-versus-previous-successful-tick snapshots,
not callback properties or queued platform events. Do not invent `onClick`,
`input.isActionJustPressed`, low-level `slider(props).value` or automatic combobox options.
Use canonical `EngineApi`, `UiApi`, `UiComponentKit`, `UiSliderControl` and node/style types from
`game api typings`; do not use handwritten `ui:any` stubs. New entry scripts
mark the canonical block; refresh it with
`game --project <game-root> api typings --update-script gameplay.luau`, which
preserves surrounding game code and rejects missing/duplicate/malformed markers.
Never point `api typings --output` at an existing game entry script.

Use `kit.createSlider({id=...,value=...,min=...,max=...,step=...})` for numeric
sliders. Create and retain each control once in `Game.start`; publish
`control.view({rect=...,trackRect=...})`, and call `control.update(api.input)`
once per `Game.update` to read the value and interaction edges. The official host
owns projected/clipped hit testing and pointer capture, including scroll-local
controls; do not duplicate screen-pointer drag mapping in projects. `view` is
UI-pure and supplies no layout or artwork. Virtual `renderItem` callbacks may
call only `view`, with persistent controls keyed by item identity. Use
`setValue` for explicit external changes or resets, and `cancel` to abandon a
drag; both ignore the old held gesture until a new start. The low-level
`slider(props)` remains compatible but does not accept value/range props or
create a numeric controller. See [the complete slider lifecycle](docs/ui-components.md#interactive-sliders).

For optional scroll drag inertia, search `"scroll inertia"` /
`"捲動慣性"` and use `scrollView`/`virtualList`/`virtualGrid` options
`inertia=true,deceleration=8`. Defaults are no inertia and exponential decay
8 inverse seconds; deceleration must be finite and in `(0,100]`. Offsets stay
clamped without elastic overscroll. Follow [the shared scroll contract](docs/ui-scroll.md)
and its target-host limits.

For font/style changes search `game api search "font size"` / `"text alignment"`
/ `"border padding"` and read [the shared style contract](docs/ui-styling.md).
Use existing typed leaves, licensed faces in `presentation.ui.fonts`, and the
official responsive model with `api.ui.getViewport()` for authored choices. Refresh
`game api typings` and the SDK when upgrading. A font/style request does not
authorize replacing the official player.

Use `kit.component({...surface={kind="panel"}})` or an image surface for ordinary
card backgrounds. The package prepends `id.."/surface"` with explicit
`background_for={component=id}` and the component's unchanged authored placement.
Children retain their coordinates and order. A component does not establish a
local origin: stage children remain 0..100/y-up; scroll content remains local
top-left/y-down. Package wrappers preserve existing scroll lifecycle/host limits.
Custom factories may carry the same
metadata on their own image/panel leaf. Search `"card background"` /
`"component overlap"` for canonical ancestor/bounds checks. Retain strict
foreground/partial overlap checks; use exact-pair policies only for deliberate
art/skin layers that do not meet containing-background semantics.

For UI layout, responsive grouping, hierarchy and visual composition, default to
semantic AI reasoning rather than mechanical coordinate rules. Infer groups from
task, role, reading order, interaction focus, lifecycle and safe-area constraints;
do not turn one screen's pixel arrangement into a runtime rule automatically.
Use relative spaces and AABB containment as an AI reasoning vocabulary: distinguish
Viewport, fixed-aspect Stage, Background layer and layout Regions before placing
leaves. Do not infer new AABB metadata or a hidden runtime layout policy from this model. AABB
can describe a proposed bound or validation question; it does not decide responsive
placement by itself.

Mechanical layout is opt-in through `createResponsiveLayout`. The user-requested
shared responsive helper is an authorized reusable package capability; using its
authored definitions requires no extra permission flow. Understand intent,
choose semantic groups and reading order, declare explicit variants/regions,
resolve them, then verify geometry and the official player. This helper does not
authorize inferring hidden rules or adding a constraint solver. Runtime validators
may report containment, overlap, overflow and hitbox failures, but must not
silently choose or rewrite the layout for the AI.
# Unone

[Portable Core SDK and platform export](docs/portable-sdk.md): ship precompiled
Core binaries and Web host templates without the Rust checkout. Web packaging is
implemented; native Windows and Android packagers now support mesh/instance/particle
players. iOS remains future work. See the native host limitations below.

Unone is an AI-native **3D game engine prototype with 2D workflows**: Rust owns engine mechanisms, while Luau owns game rules and content. The engine is still in early development; its long-term goal is complete only after seven game validations pass.

The current contract boundaries and host limitations are recorded in [Runtime contracts](docs/runtime-contracts.md). 3D transforms, cameras and presentation are an existing direction; mature 3D physics and a universal asset importer remain unfinished.

**For AI-authored games, use the official player by default.** Start effects with
the built-in [declarative particle system and Particle Lab](docs/native-particles.md):
scene JSON defines emissions and Luau uses `api.particle.*` to control them.
Custom shaders use [engine shader materials](docs/shader-materials.md), with GPU resources owned by
the presentation layer. Replacing the renderer requires an explicit project
choice. Follow the [AI workflow](docs/ai-workflow.md) and
[player export guide](docs/player-export.md); passing a headless test is only
gameplay evidence, so inspect the exported player before claiming visual completion.

The official [`@unone/ui` shared component package](docs/ui-components.md) ships
with Core and the portable SDK. Declare `"runtime_packages":{"@unone/ui":"0.2.0"}`,
discover `ui.components.info` / `ui.components.create`, then use the module's
typed text/button/slider/combobox/panel/image/component/screen constructors and
scrollView/virtualList/virtualGrid wrappers, or the same methods on a themed kit.
Search `"create button"`, `"button click"`, `"按下瞬間"`, `"滑桿"` or `"下拉選單"`
for callable controls and semantic action guidance. `input.wasPressed` /
`wasReleased` read non-consuming edges; `isDown` reads held state.
The kit composes
project-owned theme styles and instance IDs into the existing `ui.setRoot` tree;
custom Luau factories remain valid. Themes, content, state, actions, screen flow
and geometry stay in the project. Keep canonical `EngineApi` / `UiComponentKit`
types; [safely refresh a marked type block](docs/ui-components.md#keep-the-official-types-when-upgrading)
with `game --project <game-root> api typings --update-script gameplay.luau`.
[Typography and styling](docs/ui-styling.md) provide font catalogs, explicit type
sizes, alignment, wrapping, colors, padding and borders. Optional component
surfaces carry `background_for` ownership while strict inspection still reports
foreground collisions and protruding content. Core validates data; the official
Web/native hosts paint it.
The [observatory settings example](_Games/observatory-settings/README.md) was
authored independently using only a precompiled SDK, official docs and API

The [Harbor Controls example](_Games/harbor-controls/README.md) repeats that

[ScrollView / VirtualList / VirtualGrid](docs/ui-scroll.md) provide Web clipped

## Getting started from a clone

Everything below runs from the repository root. It does not need the private validation games. The public Legion Fall probe above is included under `_Games/legion-fall`.

Prerequisites:

- **Rust** — `rust-toolchain.toml` pins the channel and targets, so `rustup`
  installs the right one on first build. Nothing else to choose.
- **PowerShell** — most scripts here are `.ps1`. The one you need to get
  started also has a `.sh` version.
- **Python 3** — for `scripts/serve-player.py`, to preview the Web hosts with
  consistent JavaScript and WebAssembly MIME types on every platform.
- **Emscripten** — only if you want the Web runtime. Point
  `UNONE_EMSDK_ROOT` at it; setup and the verified version are in
  [docs/platform-toolchain.md](docs/platform-toolchain.md). Skip it until you
  need a browser.

```powershell
git clone https://github.com/Ovan741852/Unone.git
cd Unone
cargo build -p unone-cli

# The official luau-analyze is a development-time tool and is deliberately not
# committed (decision 0005). Without it `verify`'s types gate fails, so fetch
# the pinned build once; the script checks the download against a recorded hash.
powershell -File scripts/install-luau-analyze.ps1
# not PowerShell? sh scripts/install-luau-analyze.sh  (Linux, macOS, Git Bash)

cargo test --workspace
```

Then make a game. The starter is seven files and passes its own gates:

```powershell
# The engine refuses a project path containing '..', so resolve it first.
New-Item -ItemType Directory -Force ../my-game | Out-Null
$game = (Resolve-Path ../my-game).Path
cargo run -p unone-cli -- --project $game --json project init --name MyGame
cargo run -p unone-cli -- --project $game --json verify
```

`verify` should report four gates: `types`, `assets`, `tests` passing and
`layout` `not_applicable` (the starter draws no UI). That is the whole loop —
edit `scripts/main.luau`, add assertions to the tests, run `verify` again.

Keep the game outside this repository. `game api search ""` prints the complete
public API index; there is no separate list to find and no method names to guess.

Optional AI tools use the same protocol instead of adding engine-specific
dependencies. Discover and test them with `game plugin list`, `game plugin
inspect`, and `game plugin test`; see [docs/plugin-protocol.md](docs/plugin-protocol.md).
For the complete AI authoring-to-runtime handoff, use `game project sync --json`;
it composes pack, verify, and full bundle activation without requiring a Viewer.
The bundled Blender bridge is optional and can validate/stage scene data without
Blender installed. A plugin is an external process, so the Rust runtime remains
deterministic and the AI can inspect its capabilities before using it.

## Current executable vertical slice

New games use the existing `game --project <new-or-empty-directory> --json project init --name <name>`.
It creates a seven-file starter, including official-player authoring instructions,
presentation settings, a declarative particle definition, idle and Right-input
tests, and next-step argv that can be passed directly to a subprocess. Keep the game plan and engine
package outside the output directory; run git init only after init succeeds. Passing the
starter does not mean the game is complete; replace it with your own gameplay and tests.
The complete write, failure, and scene-input contracts are in the [AI development workflow](docs/ai-workflow.md).
When a search has no matches, use `game api search ""` to read the complete public index;
there is no need to find another api list or guess method names.

Run these from the engine workspace:

```powershell
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
$game = (Resolve-Path _Games/legion-fall).Path
cargo run -p unone-cli -- --project $game --json project inspect
cargo run -p unone-cli -- --project $game --json asset inspect --strict
cargo run -p unone-cli -- --project $game --json systems list
cargo run -p unone-cli -- --project $game --json api describe entity.setPosition
cargo run -p unone-cli -- --project $game --json run --frames 60
cargo run -p unone-cli -- --project $game --json test
cargo run -p unone-cli -- --json platform capabilities
cargo run -p unone-cli -- --project $game --json platform snapshot
```

Use verify as the aggregate author gate: it covers the typed check, strict asset
inspection, UI layout, and tests. The standalone asset inspect --strict command
above is for focused asset diagnosis or publication verification, not an
additional gate when verify is the selected entry point.
Use `platform snapshot` when an AI needs one current, machine-readable inventory
of runtime, renderer, host, and plugin readiness. It preserves the raw platform
report but adds explicit `verified`, `partial`, and `pending` mappings,
limitations, evidence references, and executable examples; it never starts a
plugin or claims a renderer was probed when `renderer_probe` is `not_probed`.
An AI host can also use the same Developer Protocol through a thin MCP stdio adapter:

```powershell
cargo build -p unone-cli
target/debug/game.exe --project _Games/legion-fall mcp
# Validate lifecycle, tool discovery, deterministic run, and semantic errors
.\scripts\mcp-smoke.ps1
```

MCP exists only in `unone-cli`; it is not an engine-core dependency. Tool results retain the complete `EngineResult` JSON and semantic diagnostics.

The current documented capability coverage includes Luau entrypoints, the `--!strict` contract, the official `luau-analyze` adapter, a headless fixed timestep, deterministic 2D rigid-body gravity/ground collision, Camera2D state, frame-by-frame input replay, the shared `tick_with_input` host boundary, seeded Luau random, seed/input observation digests, failed-reload fallback, scene Sprite size validation, a game-name-independent native wgpu preview, `preview --watch` script hot reload, JSON test manifests, bundle hash/cache/activation, asset-manifest/reference/active-generation queries, the host contract for resolving one asset from an active generation and reporting its verified sha256 (Rust and Web hosts share one archive format and error-code set), the `systems` contract for game-controlled engine-system selection, the native player renderer for mesh/instance batches, built-in box/sphere meshes, PNG/JPEG/WebP/static-SVG sprites, particles, Bloom, non-DOM UI and rodio/cpal audio, and the Spine/Effekseer semantic presentation layer. For complete type checking, use `game check --types`. A formal engine package places a pinned official `luau-analyze` at `bin/luau-analyze.exe`, which the `bin/game.exe` beside it finds automatically. If the tool is missing, the engine reports an explicit error instead of describing the basic contract check as complete type checking.

## Boundaries

The engine provides only necessary game mechanisms. Game rules, numbers, ViewModels, UI flow, content catalogs, download timing, and operational services stay in the game project or service layer. UI follows MVVM; ECS + systems handle high-frequency simulation.

The first Bundle version contains only a manifest, dependencies, host-provided fetch, streaming hash verification, content-addressed cache, staging, and generation activation. It does not include CDN, P2P, differential updates, or remote script execution. Fetch, retry, and platform-storage policy stay out of engine core.

## Validation games

The included Legion Fall probe stresses 3D crowds and Luau combat. Separate validation projects cover physics, cameras, input replay, scene/prefab, assets, UI, hot reload, headless tests, and AI authoring. Long-term acceptance still includes 3D Racing, Red Alert-style RTS, Dota-style Idle Battle, AVG Romance, Auto Chess, Slot Machine, and Fish Machine.

The broader acceptance matrix belongs to the separate validation suite and is not included here. If you have that suite, pass the path to its `acceptance-matrix.json` explicitly to `scripts/validate-game-matrix.ps1`; incomplete gates return a non-zero status.
