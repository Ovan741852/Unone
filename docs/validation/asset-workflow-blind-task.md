# 資產維護驗證任務

你拿到的是一份不可變引擎封裝、一份本任務與空的輸出目錄。
請只從封裝的 CLI/MCP、help、文件與型別了解引擎；不可讀引擎來源、其他遊戲、
製作計畫或製作者的測試。這不是像素渲染或七款遊戲的最終驗收。

## 要完成的內容

建立一個最小的 2D 場景作為資產維護樣本，使用你自行製作的簡單 SVG：
一張角色圖、一張場景圖。兩者分到不同內容包；角色图由兩個 entity 共用。
也可選用 https://itch.io/game-assets 上授權明確的相容素材，不強制替換已完成的
自製 SVG。須保存來源、作者、授權內容／取得日期、署名要求與檔案 hash；需付費
或授權不清楚先回報，不自行購買。這只放開素材來源，不放開遊戲程式／引擎來源。
另準備一個具 primary 與 companion 檔案的資產，檔案 bytes 可以是小型測試
內容，不宣稱它符合真實 Spine/Effekseer 格式或已能播放。

先建立與發佈初版，然後依序完成以下維護工作：

1. 保留角色的穩定 asset id，把它的圖像換成明顯不同的 SVG 內容。修改前查明
   該改哪裡、已知哪些 entity 會受到影響，以及哪些引用無法被工具保證找到。
2. 在不改 asset id 的前提下，把角色 source 搬到包含空白的另一個合法相對
   路徑；確認其放置位置、碰撞宣告及其他 scene 使用沒有被不必要地改写。
3. 修改 companion bytes，再新增一個 companion 宣告與檔案。確認能明確區分
   讀 primary 和讀 companion，不依靠試參數或搜尋引擎原始碼。
4. 刻意停在「作者檔案已改，但尚未發佈」與「已打包，但尚未啟用」兩個階段，
   記錄工具能證明的事實和不能證明的部分。不要用清除整份 cache 解決舊資產。
5. 使用封裝提供的流程發佈修訂。證明兩個內容包與所需 project/script/scene/
   manifest 同時有效；用獨立檔案 hash 比對實際可讀 bytes，不只相信成功訊息。
6. 製造一次失敗，例如缺少一個已宣告 companion 或損壞待安裝的 bundle；驗證
   沒有把不完整的新內容啟用。你自己造成並預期的拒絕是測試案例，不是產品缺陷。
7. 指出 native-local 的安裝/讀取證據能否代表 Web IndexedDB 已更新、是否能證明
   貼圖真正畫對。不要把本任務未實跑的 host 說成通過。

## 交付

保留完整命令、JSON 回傳、對照 hash、實際修改檔案清單、可重跑結果及使用評語。
同時記錄「只靠封裝是否能找出下一步」，而不只是最終檔案能否跑。

若工具/文件互相矛盾、需要猜才能完成、成功訊息與實際狀態不同，立即向主代理
回報 `[BLOCKER]`：首次命令/輸出、影響範圍、事實與推論；先停止受影響部分，
可以繼續独立案例。不要默默修引擎、改 package、跳过驗收或自己發明工具。

完成時只報 ready_for_review，明確列出未驗證的範圍；不得自行把總驗收標 passed。
