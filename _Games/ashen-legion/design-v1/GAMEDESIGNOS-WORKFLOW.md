# YesSir 的 GameDesignOS 採用方式

採用兩個已檢查並固定版本的專案 skill：

- `game-experience-analyzer`：從實機截圖、錄影建立證據、問題卡與驗收方式。
- `game-experience-density-optimizer`：把問題卡縮成一個主要變因的本機對照方案。

第一次採用與安全檢查在 `docs/reviews/2026-09-11-gamedesignos/`；這次新版檢視在 `design-v1/reviews/20260914-gamedesignos/`。原始內容沒有變更版本，也無需重複安裝。

## 何時使用

美術／UI／特效迭代先用 analyzer 檢查可讀性；數值／節奏／流派迭代先確認規則與快測結果，再用 optimizer 做單一變因的候選方案。來源碼與模擬結果另外保存，不能當成真人體驗或留存證據。

## 每輪最小產出

1. 記錄 build、來源雜湊、種子、輸入方式、尺寸與樣本範圍。
2. 保存有定位的實機證據；強制觸發的 QA 演示明確標示。
3. 至多 3 個主要問題，各寫「現象 → 證據 → 假設 → 最小改動」。
4. 每次挑一個主變因；固定其他數值、裝備、出怪與輸入。
5. 先寫通過、觀察、回退條件，再做對照。技術快測驗證正確性，真人辨識／試玩補主觀判斷。
6. 將結果、保留理由與未解問題寫回同一個 review 目錄。

本機驗證報告結構與資料來源：

```powershell
python _Games/ashen-legion/tools/verify-design-review.py
```

也可傳入其他同格式 review 目錄。此工具檢查結構與引用，不替代美術判斷；來源變更時需更新證據，不能只改雜湊讓舊结論繼續通過。

## 專案邊界

沿用 YesSir 的既有授權與 AGENTS.md：局部可逆工作持續完成，不因模板多加例行確認。玩法仍在 Luau，呈現仍在遊戲呈現層。此採用方式不需要整套 GameDesignOS runtime、全域同步或外部模型 host。

此次 ED 方案是本機候選規格，尚未實作 B 變體、招募玩家或發布 A/B 分流。沒有將待驗證方案記成已改善的結果。
