# AI 排版契約

這份規格是給 AI 讀的設計約束，不是 runtime 的座標表。AI 要先理解畫面的任務與語意，再提出分組；程式只驗證提案能不能安全呈現。

## AI 要先判斷的事情

1. **任務**：這個畫面是在選擇、確認、閱讀、比較、操作，還是等待？
2. **語意角色**：標題、說明、主要操作、次要操作、狀態、裝飾、反饋。
3. **關係**：哪些節點必須一起讀、一起出現、一起消失、一起取得焦點？
4. **閱讀方向**：繁中長文預設同一閱讀邊；數值與主要 CTA 可獨立置中。
5. **空間限制**：安全邊界、最小命中區、最小字級、最大行數、不可遮蓋的視覺內容。

## 機械式判斷是選配

預設使用 AI 的語意判斷，不把單一畫面的像素排列自動變成 runtime 規則。只有使用者明確說出下列關鍵字或同義要求，才可以提出機械式方案：

- 機械式
- 固定規則
- 座標規則
- 自動檢查
- 規則化
- deterministic
- constraint solver

即使 AI 認為機械式檢查有幫助，也只能推薦，不能直接加入。推薦時必須先說明：它解決的具體問題、作用範圍、判斷流程、失敗時的 fallback、維護成本，以及它會限制哪些 AI 判斷。使用者明確回覆同意後，才可把它加入 runtime 或驗證工具。

判斷流程固定為：

1. 先理解使用者想表達的視覺與互動意圖。
2. 先提出語意分組與解析度決策，不先寫座標規則。
3. 檢查是否真的需要可重現的機械保證，例如不能爆框或命中區必須包含。
4. 若需要，列出可選的機械規則、關鍵字、scope、fallback 與取捨。
5. 等待使用者明確同意。
6. 同意後才實作，並將檢查結果回報到元件識別碼與階層路徑。

驗證器可以回報 containment、重疊、爆框、文字溢出與命中區問題，但不可在未獲同意時自行重排、縮放或覆寫 AI 的版面提案。

## 什麼情況才算同一個 Group

元件只有在共享任務、生命週期、對齊軸或互動焦點時才分到同一 Group。靠得近、使用同一張底圖、或碰巧同一層，不足以構成群組。

Group 要描述意圖而不是座標：

- `region`：它屬於畫面的哪個功能區，以及靠哪個安全邊界。
- `flow`：stack、row、grid 或 overlay；由 AI 依內容與空間選擇。
- `widthPolicy`：同寬、內容寬、填滿可用寬度或保持比例。
- `spacing`：節奏一致、優先保留哪一段間距，以及不足時先壓縮什麼。
- `priority`：空間不足時哪些內容保留、縮短、移入詳情或延後出現。

## 相對空間判斷模型（只給 AI，不進 runtime）

排版不是把每個 Leaf 直接釘在螢幕上；AI 先用相對空間樹思考，再提出語意分組：

```text
Viewport AABB
└─ Stage AABB（固定橫版比例，可能在 Viewport 內留黑邊）
   ├─ Background AABB（包住整個場景；粒子用 Background 的座標系）
   └─ Layout Regions
      └─ Left Panel AABB（可為透明的 layout container，從上到下完整延展）
         ├─ 品牌／標題
         └─ 操作集合
```

- 這個 AABB 樹是 AI 的思考模型，不是要寫進遊戲資料，也不是要新增一套 runtime layout engine。
- `Viewport AABB` 是實際視窗；AI 先判斷固定比例 Stage 是否留黑邊，不能反過來要求 Stage 填滿。
- `Stage AABB` 是遊戲設計空間；AI 以它判斷背景、粒子、UI 的相對位置。
- `Background AABB` 表示最大的視覺語意層；粒子若屬於場景氛圍，就判斷為跟隨背景空間。
- `Layout Region` 表示需要一起縮放、對齊或重排的一組元件；它可以是不可見的語意群組，但不代表要新增可見面板或透明點擊區。
- Leaf 的位置先用父 Region 的 anchor、inset、flow 和 priority 描述；不要先把螢幕像素當成設計規則。

這套 AABB 只用來幫 AI 問對問題：父子邊界、同層重疊、安全邊界與命中區是否合理。它不會自動重排，也不會單獨決定「4:3 時按鈕置中還是靠下」。本案 runtime 只保留語意元件識別碼與既有引擎需要的繪製矩形，不接受 AABB metadata 或 layout 欄位。

以主選單為例，4:3 時 AI 先保持 `Stage → Background → Left Panel` 的語意關係，再判斷操作集合要維持中段、靠下或改成更緊湊的 flow；決策理由保留在 layout proposal 裡，runtime 不讀 AABB 來自行改位置。

## 解析度變化的決策順序

1. 先維持整個橫版 Stage 的比例與安全邊界。
2. 再檢查同一 Group 的共同寬度、對齊與閱讀順序。
3. 仍然放不下時，AI 才選擇縮短文案、改成另一個 flow、移入彈窗或重排 Region。
4. 不允許各 Leaf 自己縮放或漂移，造成同一組按鈕寬度不同、文字軸線斷裂或貼到視窗邊緣。

## AI 輸出與驗證

AI 輸出應包含 `screenIntent`、`regions`、`groups`、`leaves`、`fallbacks` 和每個選擇的理由。runtime 驗證：父框 containment、同層意外重疊、安全邊界、文字爆框、命中區與焦點順序；驗證失敗時回報節點識別碼與路徑，讓 AI 修正提案。驗證器不替 AI 偷改版面。

## 目前主選單的語意提案

`menu_left_panel` 是 hierarchy 裡的左側 layout Region；其中 `menu_brand` 將 Logo 與副標視為同一品牌 Group，`menu_actions` 只包含讀取進度、系統設定、離開三顆操作按鈕。兩組共享左側安全軸，但品牌與操作是不同語意單位。背景圖仍是場景 Leaf。AI 看到 `component_menu_brand` 或 `component_menu_actions` 時，應分別評估品牌閱讀與操作流程。這是範例，不應複製成所有畫面的固定座標。
